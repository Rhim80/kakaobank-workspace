# Naver Search — 네이버 시장·고객 조사

국내 비즈니스의 실데이터가 가장 많이 쌓인 곳은 네이버 블로그·카페인데, **AI에게는 이름으로 닫혀 있다.** `blog.naver.com/robots.txt`에 `ClaudeBot`·`Claude-SearchBot`·`GPTBot`·`OAI-SearchBot`·`PerplexityBot`이 각각 `Disallow: /`이고, `cafe.naver.com`과 `search.naver.com`은 `User-agent: *` 전면 금지다. WebFetch로 네이버 블로그를 열면 `unable to fetch`가 뜬다.

이 스킬은 그 벽 바깥의 **정식 통로** 두 개를 쓴다 — NAVER API HUB(검색·트렌드·쇼핑인사이트)와 네이버 검색광고 API(검색량·연관키워드).

## 어떤 질문에 어떤 도구인가

| 질문 | 명령 | 값의 성격 |
|---|---|---|
| 이 키워드, 한 달에 몇 번 검색되나 | `searchad.py keywords` | **절대값** (PC/모바일 분리) |
| 검색이 늘고 있나 줄고 있나 | `naver_search.py trend` | 상대값 (최고점=100) |
| 관련해서 사람들이 또 뭘 검색하나 | `searchad.py keywords` | 연관키워드 (호출당 수백 건) |
| 글이 얼마나 쌓여 있나 (경쟁강도) | `naver_search.py total` | 문서수 (AND 검색) |
| 누가 뭐라고 평가하나 | `collect_blog.py` | 블로그 목록 + 본문 |
| 누가 뭘 찾고 있나 (세그먼트) | `collect_cafe.py` | 카페 제목 + 카페명 + 회원수 |
| 이 키워드 광고 시장이 얼마짜리인가 | `searchad.py estimate` | 입찰가별 예상 노출·클릭·비용 |

## 설치 (3단계)

**1. 키 발급** — 두 곳이 별개다. 검색·트렌드만 쓸 거면 ①만 있어도 된다.

- ① **NAVER API HUB**: ncloud.com 가입 → NAVER API HUB → Application 만들기 → 쓸 API 체크(검색·검색어트렌드·쇼핑인사이트) → **[인증 정보]** 버튼에서 Client ID/Secret
- ② **네이버 검색광고 API**: searchad.naver.com 가입(**광고를 집행하지 않아도 계정만 있으면 된다**) → 도구 → API 사용 관리 → 엑세스라이선스·비밀키·CUSTOMER_ID

**2. `.env` 채우기**

```bash
cd .claude/skills/naver-search/scripts
cp .env.example .env      # 그 안 안내대로 키를 채운다
```

키는 **반드시 본인 계정으로 발급**한다. 남의 키를 받아 쓰면 계정 공유가 되고, 쿼터 초과·정책 위반 책임이 키 주인에게 간다.

**3. 연결 확인**

```bash
python3 naver_search.py total "디카페인 원두"
```

숫자가 나오면 끝. 외부 패키지 설치는 필요 없다(파이썬 표준 라이브러리만 쓴다).

## 명령

```bash
cd .claude/skills/naver-search/scripts

# 경쟁강도·트렌드 (API HUB)
python3 naver_search.py total "디카페인 원두"
python3 naver_search.py blog "디카페인 원두" --n 100         # 목록만
python3 naver_search.py cafe "디카페인 원두" --n 100
python3 naver_search.py trend "브랜드A" "브랜드B" --from 2026-01-01 --to 2026-06-30

# 검색량·연관키워드·입찰 예상 (검색광고 API)
python3 searchad.py keywords 디카페인 "디카페인 원두"         # 연관 포함 상위 30
python3 searchad.py keywords 디카페인원두 --exact             # 입력 키워드 행만
python3 searchad.py estimate 디카페인원두 --device MOBILE

# 본문·세그먼트 수집 (jsonl 저장)
python3 collect_blog.py "디카페인 원두" --n 60 --out deca.jsonl
python3 collect_blog.py "디카페인 원두" --no-body             # 목록만 = API 정식 범위
python3 collect_cafe.py "디카페인 원두" "임산부 커피" --out cafe.jsonl
```

## API가 주는 것 / 안 주는 것

```
블로그  title · link · description(115자) · bloggername · bloggerlink · postdate
카페    title · link · description(117자) · cafename · cafeurl        ← 작성일 없음
```

**온전한 것 = 메타데이터.** 제목·링크·블로거명·카페명·문서수(`total`)는 잘려 오지 않는다. 작성일은 블로그만 있다(`postdate`) — 카페엔 필드가 없어 시기 분석이 안 된다.

**안 되는 것.** 본문 · 검색 순위 · 공감/댓글 수 · **기간 지정 조회**. (검색량은 `searchad.py`가 준다.)

## 함정 4가지 (전부 실제로 당한 것)

1. **없는 파라미터는 에러 없이 무시된다.** `startDate`·`period`를 넣어도 HTTP 200이 떨어진다. 필터가 걸린 줄 알고 결과를 믿게 된다.
2. **한 쿼리 상한 1,099건 — 이건 수신 기준이고 고유 문서는 더 적다.** `display` 최대 100, `start` 최대 1000. 페이지 간 중복이 섞여 나와, 1,100건을 받으니 고유 링크는 921건이었다(같은 글이 4번까지). 기간 필터가 없어 **일회성 소급은 불가, 매일 돌려 쌓는 건 가능**. `sort=date`로 1,099건이 덮는 기간은 키워드마다 다르다 — 인기 키워드일수록 과거를 못 본다.
3. **`total`은 AND 검색이라 문서수로 쓸 수 있다.** 단 일반어가 섞인 브랜드명(예: 이름에 "이미"가 들어가는 경우)은 부풀려진다.
4. **카페 페이지 인코딩은 MS949/KSC5601.** UTF-8로 읽으면 글자가 깨지고, 깨진 텍스트엔 판정 키워드가 안 걸려 **"막힌 페이지"가 "열린 본문"으로 오판된다.** `charset`을 보고 디코딩할 것 (`collect_cafe.py`가 이미 처리).

## 스니펫으로는 내용 분석이 안 된다 (핵심)

`description`은 본문의 **5%**(115자 vs 2,400자)다. 글 앞부분도 아니고 검색어 주변도 아니다 — 글마다 고정된 발췌이고 본문 내 위치는 중앙값 45%로 흩어져 있다.

블로그 본문 28건을 열어 대조한 실측:

```
신호     스니펫   본문    놓친 비율
불만       2건    19건      89%
가격       5건    20건      75%
맥락       7건    18건      61%
```

**스니펫 기반 비율은 전부 과소추정이다.** 내용을 분석하려면 `collect_blog.py`로 본문까지 받아야 한다.

> 검증 규칙: **검색어에 넣은 말은 세지 않는다.** "○○ 맛없"으로 검색해 "맛없"을 세면 자기가 넣은 말을 세는 것이다. 중립 쿼리로 다시 돌려 대조할 것.

## 카페 — 본문은 없지만 제목이 질문이다

카페 본문은 비로그인으로 안 열린다(API 스니펫 117자 / URL은 껍데기 / RSS 404). 대신 **제목은 안 잘리고, 카페 글 제목은 그 자체가 질문이다.** 그리고 **카페명이 곧 세그먼트**다.

원본은 오염이 심해 필터가 필수다 — 한 조사에서 회원 2,867명짜리 카페가 결과의 47%를 차지했고, 부업·재테크 카페의 제휴마케팅 글이 상위에 섞였다.

**도배 지수 = 검색에 잡힌 글 수 ÷ 회원수 × 10,000.** 회원수는 카페 공개 홈의 **"멤버수" 한글 라벨**에서 읽는다(`memberCount` JSON은 없다). `collect_cafe.py`가 자동 계산하고 컷 3.0으로 거른다 — 이 컷은 근거 있는 값이 아니라 실측을 보고 잡은 것이라 **카테고리가 바뀌면 다시 맞춰야 한다.**

## 본문 수집의 선 (읽고 쓸 것)

`robots.txt`의 `User-agent: *`는 블로그 글 본문 경로를 막지 않는다. 막힌 것은 (i) AI 봇 이름 지목 (ii) "AI 학습·RAG 목적 금지" 주석이다. 주석은 프로토콜상 효력이 없지만 운영자의 의사 표시다.

국내에 관련 판례가 있다 — **잡코리아 대 사람인**(대법원). 크롤링으로 확보한 콘텐츠를 자기 영업에 쓴 것을 DB권 침해·부정경쟁행위로 인정. 다만 그건 경쟁사가 남의 DB를 상업적으로 재사용한 사건이고, 조사 목적 소량 열람과 사실관계가 같지 않다. (사건번호·판결일은 확인하지 않았다 — 인용해야 하면 원문을 먼저 확인할 것.)

실무 기준:

- 조사 목적 소량 열람과 대량 축적은 다르게 다룬다
- 수집물을 **재배포하거나 데이터셋으로 쌓아 서비스에 쓰지 않는다** (판례에서 문제된 건 읽은 행위보다 쌓아서 재사용한 것)
- 요청 간격 유지(`collect_blog.py`는 0.4초 고정 — 낮추지 말 것), 캐시로 재요청 방지
- 수집한 `*.jsonl`·본문 캐시는 **남에게 넘기지 않는다** — 도구를 공유하는 것과 데이터를 넘기는 것은 다르다

## 알아둘 일정·약관

- 구 방식 `openapi.naver.com`(네이버 개발자센터)은 API HUB로 이관 중이다. **2026-07-31** 신규 신청 차단(검색 중 쇼핑·책·전문자료는 이날 완전 종료, 대체 없음), **2027-06-30** 기존 이용자의 검색·트렌드·쇼핑인사이트 지원 종료. 지금 새로 발급하면 API HUB이므로 이 스킬은 영향 없다.
- 개발자센터 검색 API 약관이 **2026-09-07** 개정된다 — 저장·캐싱 제한(서버 최대 21일), 제3자 제공 금지, "데이터를 AI에 입력하거나 학습·개선·평가 및 노출 등에 활용하는 행위" 금지. **이건 개발자센터 약관이고 API HUB는 NCP 별도 약관 체계라 동일 조항 여부는 확인되지 않았다.** 업무에 본격적으로 쓰기 전에 본인이 가입한 쪽 약관을 확인할 것.

## 참고

- Application에 등록 안 한 API는 **401 "이 Application에서 활성화되어 있지 않습니다"**가 뜬다 → ncloud 콘솔에서 해당 API를 체크
- 쇼핑인사이트는 `naver_search.py`의 `shopping()` 함수로 제공(CLI 명령 없음). `cat_id`는 API가 이름을 안 돌려줘 네이버쇼핑 URL에서 직접 확인해야 한다
- 브랜드스토어 **리뷰** 수집·분석은 이 스킬이 아니라 `review-analyzer`
