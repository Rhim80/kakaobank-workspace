# wiring — 내 배선도를 그리고 깐다

Claude Code가 참가자와 대화하며 각자의 일 흐름을 설치한다. 사전 응답을 되읽고, 실제 자료를 가져와 확인하며, 병목 하나부터 만든다. 회사 시스템에 쓰는 것은 본인의 별도 승인 대상이다.

**시작할 때 `references/declaration.md`를 읽는다.** YAML 형식·실행상태·중복 방지·승인·이전 배선도 이관은 그 파일이 원본이다. 보조 스크립트는 Claude Code의 Bash 도구로 `bash .claude/skills/wiring/scripts/wiring.sh <명령>` 한 줄로 부른다(파이썬 이름을 직접 쓰지 않는다. 패키지 설치는 없다).

원본은 `00-system/wiring/선언.yaml`, 실행 기록은 `실행상태.yaml`이다. `배선도.md`는 생성된 보기다. 참가자에게 YAML을 작성시키지 않는다. 확정한 업무 내용을 Claude가 선언으로 옮긴다.

## 시작 — 이어갈 자리

선언이 있으면 읽고 `wiring.sh validate`를 실행한다. `진행`의 첫 false 단계부터 잇는다. YAML이 없고 기존 배선도가 있으면 reference의 이관 절차부터 따른다. 둘 다 없으면 1단계부터.

한 세션에 한 단계만 끝내도 된다. 단계 확정과 다음 단계 진행 허락을 구분한다. 파일을 쓴 뒤 다음 단계로 갈지 묻고 답을 기다린다. 각 단계 끝에 validate 후 render한다. 오류가 나면 완료로 표시하지 않는다.

## 1. 줄기 표

`references/streams.md`를 읽는다. 사전 업무파악 응답을 그대로 받는다. 없으면 핵심업무·주간흐름·사용도구·소통방식 순서로 말로 받는다.

줄기·들어오는 곳·내가 하는 것·나가는 곳을 응답 어휘로 보여준다. 없는 칸은 비우고, 희망도구·자유메모는 현재 업무 표에 넣지 않는다. 본인이 맞다고 하기 전에는 파일을 만들지 않는다.

확정하면 `assets/declaration-template.yaml`에서 선언을 만든다. `주인`(CLAUDE.md 프로필의 이름. 비어 있으면 묻는다), `줄기`, `통로`의 이름과 연결을 채우고 `진행.줄기: true`. 외부 접점이나 여러 줄기가 오는 통로는 `섞임: true`. 기록 경로는 아직 비워둔다.

## 2. 길 확인 — 실제 한 건

`references/lanes.md`를 읽고 `bash .claude/skills/wiring/scripts/check_lanes.sh`를 실행한다. 연결 목록에 표에 없는 도구가 있으면 일에 쓰는지, 어느 줄기인지 묻는다.

길은 MCP / CLI / 직접 넣기다. 공개 웹은 오늘 직접 넣기와 바꿀후보에 적는다. 한 통로 확인은 호출 세 번 안에 끝내고 안 되면 직접 넣기로 정한다. 이 단계에서 브라우저 수집기를 만들지 않는다.

MCP는 읽기 도구, CLI는 실제 명령으로 한 건을 가져온다. reference의 `store`로 원본을 등록하고 본인에게 보여준다. 실제 성공한 도구·인자 또는 argv, 조회 범위·고유키·원본 근거 경로를 통로에 적는다. 자리표시자·인증값을 쓰지 않는다. 연결 성공만으로 길을 확정하지 않는다.

직접 넣기는 본인이 `00-inbox/drop/<통로id>/`에 파일을 두는 길이다(수집 스킬의 `wiring.sh intake`가 원본함에 등록한다). 그 자리에서 한 건 넣고 intake로 등록해 본다. 시스템에 없는 회의 메모 등은 나중에 바꿀 후보로 둔다. `진행.길확인: true` 후 검사한다.

## 3. 병목 하나

표의 ‘내가 하는 것’을 보며 가장 시간이 드는 줄 또는 놓치면 큰 줄을 고르게 한다. 응답의 신경점과 대조하고, 본인이 정한 증상을 그대로 기록한다.

`병목`에 줄기 id·`통로`(그 줄기의 통로 중 병목 스킬이 받을 것)·증상·스킬 이름·입력→출력·사람의 승인기준을 적는다. `실행`도 본인과 정한다: 매 아침 수집 후 처리할 일이면 아침, 필요할 때 부르는 일이면 직접. 입력은 선언의 통로·원본에서, 출력은 별도 제안/초안까지다. `진행.병목: true`.

## 4. 깔기

`.claude/skills/` 쓰기는 Claude Code에서 별도 확인 창이 뜰 수 있다. 설치할 파일과 내용을 먼저 보여주고 허용을 받는다. 승인이 없으면 우회하지 않고 `깔기: false`를 유지한다. 기존에 만들어진 폴더와 선언은 보존하고 다음에 이어간다.

- 줄기마다 끝이 있는 일인지 계속 도는 일인지 묻고 `bash .claude/scripts/new_folder.sh 10-projects "이름" progress` 또는 `20-operations`로 만든다. 반환된 progress.md 경로를 `줄기[].기록`에 적는다.
- 통로별 원본함을 만들고, 원문은 바꾸지 않는다는 안내를 둔다. 경로·호출을 README에 다시 복사하지 않고 선언의 통로 id를 가리킨다.
- 본인이 이름 붙인 수집 스킬을 `assets/collect-skill-template.md`를 복사해 `.claude/skills/<이름>/SKILL.md`로 만든다. `<…>` 자리만 채운다. 본문에 경로·호출·명령을 새로 적지 않는다 — 템플릿이 선언과 reference를 가리키고, 직접 넣기는 `intake` 한 줄이다.
- 병목 스킬은 `assets/bottleneck-skill-template.md`를 복사해 만든다. 선언의 입력→출력 한 쌍만 처리하고 제안 파일까지만 만든다. 승인 전 progress·todo·캘린더를 바꾸지 않는다. allowed-tools는 미리 허용일 뿐 접근 금지를 강제하지 않는다.
- `00-system/선언-표면.yaml`을 읽고 `bash .claude/scripts/surfaces.sh resolve`와 `bash .claude/scripts/surfaces.sh todo validate`로 기록 위치·템플릿을 검사한다. 오류면 깔기 완료로 표시하지 않는다.
- `.claude/skills/README.md`에 만든 스킬을 등재한다. `수집스킬`·`병목.스킬`이 실물을 가리키는지 확인하고 `진행.깔기: true` 후 `wiring.sh validate --ready`를 실행한다.

## 5. 한 바퀴와 재개

`morning`을 Skill 도구로 호출한다. 실제 받은 자료 최소 세 건, 둘 이상의 줄기를 포함한다. 만든 예시로 현장 검증을 대체하지 않는다.

정상 처리뿐 아니라 같은 자료 재수집 때 원문·건수·상태가 중복되지 않는지, 제안 후 멈췄다가 queue에 승인대기가 다시 나오는지 확인한다. 수집 실패 검사에서는 마지막 성공 지점이 유지되는지 본다. 테스트용 실패는 임시 작업공간에서 하고, 실제 사내 서비스 설정을 망가뜨리지 않는다.

승인한 항목의 기록·todo 반영, 기한의 캘린더 확인, ripple과 daily-note 호출을 확인한다. `한바퀴-기록.md`에 입력 자료·실행 명령·결과·미검증 범위를 적는다. 선언값을 다시 베끼지 않는다. 사내 MCP나 실제 참가자의 답을 대역 검사만으로 통과시켰다고 하지 않는다.

완료하면 `진행.한바퀴: true`, `돌아보기`의 첫 날짜와 먼저 바꿀 것을 받는다. validate와 render 후 ‘흐름은 돈다, 다음은 첫 돌아보기에 본다’로 마친다. 뒤의 돌아보기·실행·위키 축적은 참가자의 실제 업무를 하며 이어간다.

## 스킬 자체 검증

변경 후 `python3 .claude/skills/wiring/scripts/test_wiring.py`를 실행한다. 기계 검사가 잡는 것과 못 잡는 것은 `references/declaration.md` 「검사 범위」, Claude Code 대화 시험 기록은 `references/validation.md`에 있다. 스크립트 통과를 사내 MCP·실제 참가자 검증으로 바꾸어 말하지 않는다.
